# 架构设计

## 组件总览

```mermaid
flowchart LR
    subgraph 主控端 client(浏览器)
        UI[网页 UI<br/>画面渲染/延迟显示/画质选择]
        JSCrypto[SubtleCrypto<br/>PBKDF2+HKDF+AES-GCM]
    end

    subgraph 被控端 host(常驻进程)
        Cap[capture.py<br/>mss 截屏 + JPEG 编码]
        Inj[input_injector.py<br/>pynput 鼠标键盘注入]
        Clip[clipboard.py<br/>剪贴板轮询同步]
        Adapt[common/adaptive.py<br/>自适应画质控制器]
        Srv[server.py<br/>WebSocket 会话/加解密/流控]
    end

    subgraph 中转服务器 relay(可选,部署在公网)
        Relay[server.py<br/>按会话码配对 + 纯字节转发]
    end

    UI <--> JSCrypto
    JSCrypto <-- 直连: ws://host:port --> Srv
    JSCrypto <-- 中转: ws://relay:port --> Relay
    Relay <--> Srv
    Srv --> Cap
    Srv --> Inj
    Srv --> Clip
    Srv --> Adapt
```

三个组件都可以独立运行,彼此之间只通过 WebSocket 通信:

- **host**(`host/`):跑在"被控制"的电脑上,Python 常驻进程,负责屏幕采集、
  输入注入、剪贴板同步,以及作为 WebSocket 服务端(直连模式)或客户端
  (中转模式)。
- **client**(`client/`):跑在"发起控制"一方,是一个纯浏览器网页应用;
  `client/main.py` 只是本地起一个静态文件服务器 + 自动打开浏览器的便捷
  启动器,真正的连接/解密/渲染逻辑全部在 `client/static/app.js` 里用
  浏览器原生 API 实现,不需要安装任何桌面 GUI 依赖。
- **relay**(`relay/`):可选的中转/穿透服务器,部署在有公网 IP 的服务器
  上,解决 host 和 client 都在 NAT/防火墙之后、无法直连的场景。relay
  不参与加密握手、看不到任何明文内容,只做"按会话码配对 + 原样转发密
  文字节"。

## 为什么 client 是网页而不是桌面程序

1. **零安装**:用户不需要在"发起控制"的这台电脑上装任何东西,双击
   `client.exe`(或 `python -m client.main`)自动打开浏览器即可连接,
   天然跨平台(Windows/macOS/Linux/甚至手机浏览器)。
2. **加密算法可移植**:浏览器原生 `SubtleCrypto` 支持 PBKDF2、HKDF、
   AES-GCM,不需要在 JS 里手写/引入第三方椭圆曲线密码学实现(见
   `common/crypto.py` 顶部关于"为什么不用 ECDH"的说明)。
3. **渲染管线现成可用**:`<canvas>` + `createImageBitmap` 解码 JPEG 效率
   很高,不需要自己写图像解码器。

被控端(host)则必须是原生进程,因为屏幕采集、鼠标键盘注入是浏览器沙箱
无法做到的系统级操作。

## 通信协议

详见 `common/protocol.py`(权威实现)与 `client/static/app.js` 的对应
JS 实现,`relay` 侧协议见 `docs/relay_protocol.md`。核心要点:

1. **握手**:host 发送明文 `kex_init`(内含随机 salt),双方各自用
   `PBKDF2-HMAC-SHA256(密码, salt, 200000 次迭代)` 派生出中间密钥,再
   经 `HKDF-SHA256` 派生出最终的 32 字节 AES-256-GCM 会话密钥。密码永远
   不在网络上传输。client 收到 `kex_init` 后无需再回复握手消息,直接
   发送第一条用会话密钥加密的 `hello`;host 解密成功即视为密码正确
   (AEAD 认证失败本身就是"密码错误"的隐式判定,不需要额外设计一轮
   "验证密码"的消息)。
2. **加密**:握手完成后,所有消息(控制信令 JSON 与视频帧二进制数据)
   都封装为 `[12字节随机nonce][AES-256-GCM密文]` 的二进制 WebSocket
   帧,AAD 使用握手时的 salt(把密文和这一次会话绑定,防止跨会话拼接/
   混淆攻击)。这意味着**即便通过中转服务器转发,relay 也看不到屏幕
   画面、按键或剪贴板的明文内容**。
3. **视频帧**:JPEG 编码,附带 16 字节头部(序号/时间戳/宽高/质量/
   编码格式);client 收到并解码后立即回一条 `frame_ack`,host 用这个
   往返延迟驱动自适应画质(见下文)。
4. **鼠标坐标**用 0~1 归一化坐标传输,host 端按"当前真实屏幕分辨率"
   还原为像素坐标——这样无论视频当前用多大的缩放比例编码,点击位置始终
   精确。
5. **按键**:可打印字符走 `KeyboardEvent.key`(点按语义,兼容各种键盘
   布局/输入法产生的字符);方向键/功能键/修饰键走 layout 无关的
   `KeyboardEvent.code`,并保留完整的按下/抬起语义,以支持组合键与
   长按。

## 弱网稳定性设计(项目的核心目标)

远程桌面在弱网下最常见的失败模式不是"卡",而是**延迟越来越高、操作
越来越不跟手**——本质原因是发送端在网络跟不上时仍然持续产生新帧,数据
在缓冲区里越积越多(bufferbloat),用户看到的画面和操作反馈就会越来越
滞后于当下。本项目的应对思路,参考了 TCP Vegas/BBR 等拥塞控制算法的
核心理念,以及 RustDesk / AnyDesk / TeamViewer / 向日葵等现有方案在弱网
场景下的通用做法:

1. **一帧一确认的窗口流控**(`host/server.py` 的 `_frame_loop`):host
   发出一帧后,必须等到 client 的 `frame_ack`(或超时)才会发下一帧。
   这保证了"在途"的画面数据量始终有界,网络越差,自然发送得越慢,而
   不是把网络暂时不能消化的数据堆积在缓冲区里——这是保证操作响应性的
   关键,比"画质多高"更优先。
2. **快降慢升的自适应画质**(`common/adaptive.py`):
   - 用 `frame_ack` 的往返延迟做指数滑动平均(EWMA),映射到 5 个画质
     档位(极速/流畅/均衡/清晰/高清)。
   - 网络变差时**立刻**降档(必要时一次多降一档);网络转好后需要
     **连续 5 次**采样都达标才升一档,并且在发生一次"帧确认超时"这种
     严重拥塞信号后会进入一段冷却期,期间禁止升档——避免网络抖动导致
     画质来回跳变。
   - 默认是"智能模式"(自动),用户也可以在网页里手动固定某个档位,
     或自定义分辨率缩放/JPEG 质量/最大帧率三个参数。
3. **心跳延迟独立测量**:client 每秒发一次 `ping`,与视频帧流控解耦,
   即使当前网络差到画面卡住,用户也始终能看到准确的延迟数字,而不是一
   个"卡死不更新"的假象。
4. **断线自动重连**:client 检测到 WebSocket 断开后,用指数退避
   (1s→2s→4s→…→10s 封顶)自动重新发起握手,无需用户手动干预——弱网
   下短暂断线是常态,自动重连是"稳定连接"这个目标的必要组成部分。
5. **只保留最新帧,不做无谓重传**:协议设计上没有"必须可靠送达"的视频
   帧重传机制——旧画面即使丢了也没有价值,重传只会让延迟更差;真正需要
   可靠送达的是控制信令(鼠标/键盘/剪贴板),这些消息体积很小,在
   WebSocket/TCP 上天然可靠,不需要额外的应用层重传逻辑。

## 与现有方案的对比

| | 本项目 | TeamViewer / AnyDesk / 向日葵 | 原生 VNC | Windows 远程桌面(RDP) |
|---|---|---|---|---|
| 弱网自适应 | 是(快降慢升,优先保操作响应) | 是(闭源,具体策略不公开) | 基本没有 | 有,但更偏局域网/专线场景 |
| 端到端加密 | 是(口令派生 AES-256-GCM,中转服务器不可见明文) | 是(闭源实现) | 通常没有(需自行套 SSH/TLS) | 有(TLS/NLA) |
| 穿透 NAT | 是(可选中转服务器) | 是(依赖官方服务器) | 否(需自行做端口转发) | 否 |
| 客户端形态 | 浏览器网页,零安装 | 需安装桌面客户端 | 需安装 VNC viewer | Windows 自带 |
| 开源可审计 | 是 | 否 | 是(实现众多,质量不一) | 否 |
| 主要目标场景 | 高延迟/弱网下的稳定可操作性 | 通用远程协助 | 局域网/开发者场景 | 企业内网/云桌面 |

## 安全设计取舍说明

- 使用口令派生密钥(PBKDF2+HKDF)而非 ECDH 临时密钥交换,因此**不具备
  前向安全性**:如果密码事后泄露,理论上可以解密被截获的历史流量。这
  是为了让浏览器端只依赖标准、广泛支持的 SubtleCrypto 算法,避免在 JS
  里手写/移植椭圆曲线密码学代码带来的正确性风险。如果需要更强的前向
  安全性,建议在直连模式下用反向代理套一层 `wss://`(TLS)。
- **会话内防重放**:AES-GCM 只保证篡改会被发现,不保证同一条密文不会被
  原样重发。`SessionCipher`(host 与 client 两侧实现一致)会记住会话期间
  见过的 nonce,拒绝重复值,防止恶意中转方或链路中间人截获一条合法密文
  (例如一次点击/按键)后原样重放。
- host 侧对握手失败按来源 IP 做限速(60 秒内失败 5 次封禁 120 秒),
  减缓密码暴力破解。**中转模式下 host 观察到的来源 IP 其实是 relay 自身
  的地址**,relay 又不能可信地把真实来源转交给 host(转交的信息本身也
  可能被恶意/被攻陷的 relay 伪造),所以这套限速在中转拓扑下本质上是
  "按这个 host 的中转身份整体限速",而不是真正意义上按攻击者身份限速:
  触发封禁会连带影响此后经由同一 relay 的所有人。为降低这个副作用的
  影响面,中转模式下用了一个明显更短的封禁时长(15 秒,直连模式仍是
  120 秒);根本上的缓解手段是使用默认生成的、有足够长度/熵的密码与
  会话码,而不是依赖限速本身做强保证。
- kex_init 是握手阶段唯一的明文消息,client 会对其中的 `iterations`
  (必须落在 `[100000, 2000000]`)与 `salt` 长度做范围校验,拒绝异常值——
  防止链路中间人把 KDF 迭代次数改小,诱导 client 用被弱化的密钥加密首条
  `hello` 消息,从而降低离线暴力破解的门槛;也防止用超大 salt/iterations
  拖垮浏览器标签页。握手只允许发生一次,建立会话后再次收到的 `kex_init`
  会被直接忽略。
- host 对输入注入相关的控制消息做了防御性加固:鼠标滚轮单次幅度有上限
  (防止被放大成大量阻塞式系统调用)、剪贴板写入被移出事件循环线程且限制
  处理频率、任何输入注入库(pynput/mss/pyperclip)抛出的非预期异常都会
  被捕获记录而不会打断整条会话。
- relay 的转发限速对 host→client / client→host 两个方向分别计算独立的
  预算,不共用同一个令牌桶。
- relay 完全不掌握密码、也无法解密任何转发的内容,即使 relay 服务器
  被攻破,泄露的也只是"哪个会话码在什么时间转发了多少字节",没有屏幕
  画面/按键/剪贴板内容。
