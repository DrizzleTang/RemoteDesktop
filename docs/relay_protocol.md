# 中转服务器(relay)协议规范

relay 只负责在无法直连(NAT/防火墙)时,把 host 与 client 的原始 WebSocket
消息互相转发,**不参与、不理解**双方的应用层握手与加密内容——它转发的是
不可读的密文与握手数据,天然无法窥探屏幕画面、按键或剪贴板内容。

## 连接与注册

host 与 client 都通过 `ws://<relay-host>:<relay-port>/` 连接到 relay。
连接建立后,**必须立即**发送且仅发送一条文本 JSON 消息作为注册请求:

```json
{"t": "relay_register", "role": "host", "id": "AB12CD34", "v": 1}
```

- `role`: `"host"` 或 `"client"`。
- `id`: 会话配对码,正则 `^[A-Za-z0-9]{4,32}$`,由 host 端生成并展示给用户,
  用户在 client 端输入同一个 id 即可配对。
- `v`: 协议版本号,当前为 `1`。

### 校验规则(relay 侧)

- 首条消息必须是文本帧、可解析为 JSON、且体积不超过 2048 字节;否则直接关闭连接,不回复。
- `id` 不匹配正则 -> 回复 `{"t":"relay_error","reason":"invalid_id"}` 后关闭连接。
- `role` 不是 `host`/`client` -> 回复 `{"t":"relay_error","reason":"invalid_role"}` 后关闭。

### host 注册

- 若该 `id` 当前没有正在等待配对的 host -> 记录 `id -> host连接`,回复
  `{"t":"relay_registered"}`,host 进入"等待 client"状态。
- 若该 `id` 已被占用(无论是等待中还是已配对) -> 回复
  `{"t":"relay_error","reason":"id_in_use"}` 后关闭连接。
- 等待中的注册若超过 **10 分钟** 仍未被配对,relay 应主动清理(关闭连接、
  回收 id),避免内存泄漏(用一个后台定时任务定期扫描)。

### client 注册(配对)

- 若该 `id` 存在一个"等待中"的 host -> 将 host 与 client 标记为已配对,
  **分别**向 host 与 client 发送 `{"t":"relay_paired"}`,随后 relay 进入
  纯转发模式(见下文)。
- 若不存在 -> 回复 `{"t":"relay_error","reason":"host_not_found"}` 后关闭。

## 转发模式(配对成功之后)

配对成功后,relay 对这条连接上后续收到的**每一条消息**(无论文本帧还是
二进制帧,均含 host<->client 之间的密钥交换与加密后的应用层数据),原样
转发给配对的另一端,不做任何解析、修改、缓冲合并或速率控制之外的处理。

- relay 可以对每个已配对会话做**限速**(建议:例如最高约 8 MB/s 或可配置),
  超出时简单地丢弃当前这条消息(不阻塞、不缓冲队列无限增长),这是保证
  "弱网下依然稳定"的一部分——宁可让上层的自适应画质因为超时降级,也不要
  让 relay 自己变成无限增长的缓冲区(bufferbloat)。
- 任意一端断开连接 -> relay 应主动关闭另一端连接(WS Close),不注入任何
  额外消息;两端各自的重连逻辑会处理后续重连。
- 配对关系结束后,`id` 应被释放,允许重新注册使用。

## 安全与资源限制建议

- relay 应对单个来源 IP 的注册频率做基本限流(例如每分钟不超过 20 次
  `relay_register`),防止 id 空间被扫描/耗尽攻击占用。
- relay 应设置合理的最大并发连接数与每连接空闲超时(例如 60 秒内未完成
  注册就断开),避免恶意连接耗尽资源。
- relay 自身**不做**身份认证与内容加密——真正的访问密码校验发生在
  host<->client 的应用层握手中(见 `common/crypto.py`),relay 无法、也不
  需要知道密码。
